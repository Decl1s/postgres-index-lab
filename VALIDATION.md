# Что я фактически проверил

28.10.2026 · версия 0.1.0 · Linux x86_64 · CPython 3.12.15 · PostgreSQL 16.15.
Я запускал уже установленные binaries в собственной временной БД без TCP.
Рабочие базы и постоянные службы не использовал.

| Моя проверка | Подтверждённый результат |
| --- | --- |
| Быстрые тесты | Я прошёл 21 unittest: диапазоны, JSON plans, invalid numbers, корректный median, buffers без двойного счёта, bundle, повреждения, lock и отказ публикации |
| PostgreSQL integration | Я прошёл 6 тестов: равенство строк, 60004 заказа, границы, замеры, bundle, отказ SQL, PG-env изоляция и cleanup после исключения |
| Первый CLI demo | Я получил 50 одинаково упорядоченных строк; пять измерений до и после, по одному исключённому warm-up |
| Фактический план | Я увидел Limit → Sort → Seq Scan до индекса и Limit → Index Only Scan после него |
| Наблюдаемое время | Median до 5.194 ms, после 0.047 ms; до min/max 4.287/5.375, после 0.044/0.056 |
| Buffers | Shared hit/read первого измерения: 1771/0 до и 5/0 после; я не суммировал parent и children |
| Контрольные границы | Я получил только order_id 60001 и 60004; 60002 на верхней границе и 60003 до нижней исключены |
| Цена индекса | Я измерил 1810432 bytes дополнительного индекса |
| Verify | Я подтвердил состав шести файлов, размеры и SHA256 результатов |

Я не задаю обязательный выигрыш latency или обязательный scan в тестах.
План, статистика и время могут отличаться. Эти цифры относятся к первому
прогретому локальному опыту, а не к чужой ОС, cold cache или production нагрузке.
Время загрузки, VACUUM, сборки индекса и запуска psql в execution_ms не входит.

В `scripts/smoke.py` я проверяю CLI, verify и отказ перезаписи прежнего результата.
В `scripts/zip_smoke.py --postgres` я выполняю unit и небольшой реальный опыт из
распакованного архива. Финальные receipts этих прогонов и публичного выпуска
я сохраняю в локальном журнале серии. Source-only упаковщик сверяет allowlist,
UTF-8, отсутствие контактов/приватных путей/маркеров секретов и каждый файл ZIP.

## Как я воспроизвожу проверки

```bash
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python -m unittest discover -s tests -p integration.py -v
.venv/bin/python scripts/smoke.py
.venv/bin/python scripts/zip_smoke.py --postgres
```

Я не встретил упавших бизнес-проверок в первых завершённых unit/integration.
Я уточнил явный порядок json_agg при разборе кода до их завершения; изменения
результата или выдуманного инцидента в отчёт не добавлял.

В CI я настроил Ubuntu 24.04 / Python 3.12.15 для полного PostgreSQL-профиля и
Windows 2025 / Python 3.12.10 для unit/ZIP. Наличие workflow не равно успеху
запуска: фактический статус я смотрю в [Actions](https://github.com/Decl1s/postgres-index-lab/actions).
Релиз зависит от обоих check и содержит исходный ZIP/SHA256SUMS; я не меняю тег
после публикации.

Полную лабораторию на Windows/macOS, power loss, hostile races, нагрузку,
произвольный SLA, внешнюю БД и холодный диск я не проверял.
